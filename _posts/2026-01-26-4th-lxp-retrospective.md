# LearnFlow 프로젝트 4차 회고

## 개요

| 항목 | 내용 |
|------|------|
| 프로젝트 기간 | 2026.01.05 ~ 2026.01.19 (2주) |
| 담당 도메인 | Lecture 도메인 리팩토링 (3차 연속) |
| 주요 작업 | 커리큘럼 생성 로직 개선, 인프라 이슈 해결 |
| 기술 스택 | Java 17, Spring Boot 3.5.8, Spring Data JPA, MySQL |

4차 스프린트는 3차에서 구현했던 Lecture 도메인을 **실제 운영 환경에 맞게 리팩토링**하는 작업이 중심이었다. 특히 커리큘럼 생성 로직의 구조적 문제를 발견하고 해결하면서, 애그리게이트 설계에 대한 깊은 고민을 하게 되었다.

---

## 나의 담당 기능

### 1. 커리큘럼 생성 로직 리팩토링

이번 프로젝트 기간 동안 가장 많은 시간을 쏟은 부분이다. 단순히 코드를 고치는 수준이 아니라, **설계 관점에서의 트레이드오프**를 직접 체감했다.

#### 1.1 한 번의 요청으로 모든 것을 처리하려던 문제

**기존 설계의 문제점**:
- 강의(Lecture) 생성 시 Chapter, Lesson, Quiz를 **한 번의 API 요청으로 모두 생성**하는 구조
- 유저 편의성을 고려한 설계였지만, 실제 운영 규모의 커리큘럼을 처리하려니 문제 발생
- 예시: Lecture 하나당 Lesson 80개, Quiz 100개 이상, Video 60개 이상 존재 가능
- 한 번의 삽입 과정에서 각각이 생성되는 과정에 **트랜잭션 lock이 발생**
- 서버가 다른 로직도 처리해야 하는데 하나의 큰 작업이 블로킹되는 문제

**개선 방향**:
- 강의 생성과 커리큘럼 구성을 분리
- Chapter/Lesson 단위로 점진적 생성이 가능하도록 API 재설계
- Lecture 생성 후 커리큘럼 페이지에서 나머지 작업을 진행할 수 있도록 구조 변경

#### 1.2 애그리게이트 분리의 함정 - 분산 트랜잭션 문제

가장 큰 학습 포인트는 **애그리게이트를 강제로 분리했을 때의 위험성**이었다.

**초기 접근**:
- DDD 원칙에 따라 Lecture-Chapter-Lesson, Quiz를 독립된 애그리게이트로 분리 시도
- 혹시 모를 MSA 확장을 고려한 설계

**문제 발견**:
이들은 **강한 생명주기 결합**을 가지고 있었다:
- Chapter는 Lecture 없이 존재할 수 없다
- Lesson은 Chapter 없이 존재할 수 없다
- Quiz는 Lesson과 함께 생성되어야 한다

**분산 트랜잭션의 위험성**:
- 애그리게이트를 분리하면 각각의 저장이 별도 트랜잭션으로 처리됨
- 부분 실패 시 데이터 정합성이 깨지는 문제 발생
- 네트워크는 항상 실패의 가능성이 존재
- 보상 트랜잭션을 구현하는 것은 복잡도를 크게 높임

**Quiz의 특수성**:
- Lecture/Chapter/Lesson과 달리 프론트엔드 측의 요청에 따라 Lesson 생성 과정에서 한 번에 생성되는 구조
- 굳이 분리할 이유가 없음

**최종 결정**:
강한 결합이 명확한 경우, 애그리게이트 분리가 오히려 더 큰 위험을 만든다. Lecture를 루트로 하는 단일 애그리게이트로 유지하되, 내부 구조를 잘 설계하는 방향으로 결정했다.

**추가 고려 사항**:
- Lecture가 단일로 가지는 책임이 다양함
- Lesson은 자체가 video를 가지거나 퀴즈를 가지는 기능적 요소를 많이 가짐
- 이러한 복잡성을 고려하면, 향후 필요 시 (Lecture / Chapter / Lesson+Quiz) 또는 (Lecture / Chapter+Lesson+Quiz) 정도로 분리하는 것도 하나의 방법이 될 수 있음
- 다만 현재는 분산 트랜잭션의 위험성이 더 크다고 판단하여 단일 애그리게이트 유지

#### 1.3 enum은 DDL에 자동 반영되지 않는다

**문제 상황**:
리팩토링 중 `LectureStatus` enum에 새로운 값을 추가했는데, 테스트 환경에서는 잘 동작하다가 **운영 DB에서 오류**가 발생했다.

**원인 분석**:
- JPA의 `@Enumerated(EnumType.STRING)`은 Java enum을 문자열로 저장할 뿐
- **DB의 CHECK 제약조건이나 ENUM 타입을 자동으로 업데이트하지 않음**
- 테스트 환경에서는 매번 새로 생성해서 문제가 없었지만, 운영 환경에서는 스키마 변경이 필요했음

**해결 방법**:
enum 변경 시에는 반드시 **마이그레이션 스크립트로 DB 스키마를 직접 수정**해야 한다는 점을 배웠다.

### 2. NGINX + HTTPS 환경에서 PUT 요청 이슈

**문제 상황**:
로컬에서는 정상 동작하던 PUT 요청이 **NGINX + HTTPS 환경에서만 실패**하는 현상이 발생했다.

**원인 분석**:
- **CORS Preflight** 문제였다
- PUT, DELETE 같은 "비단순 요청"은 브라우저가 먼저 OPTIONS 요청을 보내 서버가 허용하는지 확인
- GET은 예비 검사 없이 바로 전송되는 "단순 요청"이라 성공했지만
- PUT은 CORS 설정에서 승인받지 못해 차단됨

**해결 방법**:
Spring CORS 설정에 프론트엔드 HTTPS 도메인을 Origin으로 추가하고, PUT과 OPTIONS 메서드를 명시하여 해결했다.

### 3. JPA 페이지네이션 구현

**요구사항**:
강의 목록 조회에 페이지네이션이 필요했다.

**구현 방법**:
- JPQL과 `Pageable`을 조합하면 **자동으로 COUNT 쿼리와 LIMIT/OFFSET이 적용**됨

**Cursor 기반 vs Offset 기반 선택**:
- **Offset 기반을 선택**한 이유:
  - 무한 스크롤이 아닌 페이지 번호 방식 UI
  - 데이터 규모가 크지 않아 Offset의 성능 문제가 크지 않음
  - 구현 단순성

### 4. Cascade Persist와 ID 반환 타이밍 문제

**문제 상황**:
Lecture 저장 후 **자식 엔티티(Chapter, Lesson)의 ID가 바로 반환되지 않는** 문제가 있었다.

**원인 분석**:
- `GenerationType.IDENTITY` 전략과 `CascadeType.PERSIST`의 조합에서 **flush 타이밍이 불일치**
- IDENTITY 전략은 INSERT 시점에 ID가 생성되는데
- Cascade로 저장된 자식들은 명시적 flush 전까지 INSERT가 지연됨
- 강제적으로 flush & save를 사용하는 방향도 시도했지만, 더티체킹을 통한 방식에서의 딜레이로 인해 여전히 문제가 존재

**해결 방법**:
ChapterRepository/LessonRepository를 분리하여 직접 save()를 호출하는 방식으로 해결했다.

## 핵심 설계 결정

### 애그리게이트 결합/분리 판단 기준

이번 스프린트를 통해 정리한 판단 기준:

| 상황 | 권장 |
|------|------|
| 생명주기가 완전히 동일 (생성/삭제가 함께) | 단일 애그리게이트 |
| 독립적 조회/수정이 빈번 | 분리 고려 |
| 분리 시 트랜잭션 정합성 보장 어려움 | 단일 유지 |

**핵심 교훈**: "분리하면 좋을 것 같다"는 막연한 생각보다, 분리했을 때의 구체적 위험을 먼저 따져봐야 한다.

**Quiz와 Lesson의 관계**:
- Quiz와 lesson을 분리한 상태에서 합쳤는데, 퀴즈가 생성될 때 lesson에 종속된 상태로 생성됨
- 해당 lesson이 삭제된다면 Quiz들이 사라지는 게 맞는 구조
- 만약 문제은행 방식의 퀴즈가 따로 정의되어 있고, lesson이 Quiz를 호출하는 방향이었다면, 약한 결합으로 두고 애그리게이트를 분리해서 정의했을 것 같다

**배경**:

## 개선할 점

### 1. 테스트 환경과 운영 환경의 차이 인지

**현재 상황**:
- enum 문제는 테스트 환경에서는 update 속성으로 인해 문제가 없었지만, 운영 환경에서는 스키마 변경이 필요했음
- 환경 차이를 더 일찍 인지하지 못함

**개선 방향**:
- 운영 환경과 유사한 테스트 환경 구성
- 스키마 변경이 필요한 경우를 사전에 체크
- 마이그레이션 스크립트 작성 습관화
- 더 명확한 관리가 필요하다면 마이그레이션 툴도 도입 고려할 가능성도 존재

### 2. 설계 결정 시 더 깊은 고민

**현재 상황**:
- 애그리게이트 분리를 시도했다가 되돌리는 과정에서 시간 소비
- 초기 설계 단계에서 트레이드오프를 더 깊이 고민하지 못함

**개선 방향**:
- 설계 단계에서 분리 시 발생할 수 있는 구체적 위험을 먼저 검토
- 트레이드오프를 명확히 문서화
- 작은 프로토타입으로 검증 후 결정

## 개인적인 성찰

### 같은 도메인을 깊게 파는 경험

3차에서 4차로 이어지면서 **같은 도메인을 깊게 파는 경험**이 되었다. 처음 설계할 때는 쉽게 생각한 문제들이 실제 데이터와 운영 환경에서는 생각과 다르게 드러났다.

특히 애그리게이트 설계에서 느낀 점은, 이것도 결국 **트레이드오프의 문제**라는 것이다. 소프트웨어 설계에서도 모든 것을 만족시키는 정답은 없다. 결합도를 낮추면 분산 트랜잭션 위험이 올라가고, 트랜잭션 안정성을 높이면 결합도가 올라간다.

중요한 건 **현재 상황에서 어떤 가치가 더 중요한지 판단하고, 그 근거를 명확히 하는 것**이다. 그리고 해당 리스크가 **타당한 리스크이고, 덜 크리티컬한 리스크인지 판단하는 것**이다.

### 리팩토링의 본질

리팩토링은 단순히 코드를 예쁘게 고치는 게 아니라, **설계 결정을 재검토하고 더 나은 방향을 찾는 과정**임을 배웠다. 처음 설계할 때는 보이지 않았던 문제들이 실제 운영 환경에서 드러나고, 그 과정에서 더 나은 설계를 찾아가는 것이 리팩토링의 가치인 것 같다.

### "왜"에 대한 탐구

이번 스프린트는 분산 트랜잭션의 위험성, CORS의 동작 방식, JPA의 내부 메커니즘 등 **"왜 이렇게 동작하는가"**에 대한 이해가 깊어진 시간이었다. 단순히 문제를 해결하는 것이 아니라, 왜 이런 문제가 발생했는지, 왜 이렇게 해결해야 하는지에 대한 근본적인 이해를 추구하는 것이 중요함을 느꼈다.

## 결론

4차 스프린트는 "만들기"보다 "다듬기"에 집중한 시간이었다. 리팩토링은 단순히 코드를 예쁘게 고치는 게 아니라, **설계 결정을 재검토하고 더 나은 방향을 찾는 과정**임을 배웠다.

분산 트랜잭션의 위험성, CORS의 동작 방식, JPA의 내부 메커니즘 등 **"왜 이렇게 동작하는가"**에 대한 이해가 깊어진 스프린트였다. 특히 애그리게이트 설계에서 트레이드오프를 직접 체감하며, 설계 결정의 중요성과 그 근거를 명확히 하는 것의 가치를 배웠다.

같은 도메인을 깊게 파는 경험을 통해, 처음 설계할 때는 보이지 않았던 문제들이 실제 운영 환경에서 드러나고, 그 과정에서 더 나은 설계를 찾아가는 것이 리팩토링의 본질임을 깨달았다.

앞으로도 설계 결정 시 트레이드오프를 명확히 인식하고, "왜"에 대한 탐구를 멈추지 않으며, 한 걸음씩 성장해 나가겠다.
